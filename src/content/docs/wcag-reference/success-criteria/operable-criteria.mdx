# Operable Success Criteria

User interface components and navigation must be operable. This means that users must be able to operate the interface (the interface cannot require interaction that a user cannot perform).

## Overview

The Operable principle includes 20 success criteria across Level A, AA, and AAA:

- **Level A**: 11 criteria
- **Level AA**: 7 criteria
- **Level AAA**: 5 criteria

This reference focuses on the Level A and AA criteria that are most commonly required.

## Guideline Sections

The Operable principle is organized into five guideline sections:

### 2.1 Keyboard Accessible

Make all functionality available from a keyboard.

- [2.1.1 Keyboard (Level A)](./operable/keyboard-accessible.mdx) - All functionality must be operable through a keyboard interface
- [2.1.2 No Keyboard Trap (Level A)](./operable/keyboard-accessible.mdx#212-no-keyboard-trap-level-a) - Users must be able to navigate away from any component using only the keyboard
- [2.1.4 Character Key Shortcuts (Level A)](./operable/keyboard-accessible.mdx#214-character-key-shortcuts-level-a) - Provide alternatives for single-key shortcuts

### 2.2 Enough Time

Provide users enough time to read and use content.

- [2.2.1 Timing Adjustable (Level A)](./operable/enough-time.mdx) - Allow users to turn off, adjust, or extend time limits
- [2.2.2 Pause, Stop, Hide (Level A)](./operable/enough-time.mdx#222-pause-stop-hide-level-a) - Provide controls for moving or auto-updating content

### 2.3 Seizures and Physical Reactions

Do not design content in a way that is known to cause seizures or physical reactions.

- [2.3.1 Three Flashes or Below Threshold (Level A)](./operable/seizures-physical-reactions.mdx) - Limit flashing to safe levels

### 2.4 Navigable

Provide ways to help users navigate, find content, and determine where they are.

- [2.4.1 Bypass Blocks (Level A)](./operable/navigable.mdx) - Provide a mechanism to bypass repeated content
- [2.4.2 Page Titled (Level A)](./operable/navigable.mdx#242-page-titled-level-a) - Ensure pages have descriptive titles
- [2.4.3 Focus Order (Level A)](./operable/navigable.mdx#243-focus-order-level-a) - Maintain logical focus order
- [2.4.4 Link Purpose (In Context) (Level A)](./operable/navigable.mdx#244-link-purpose-in-context-level-a) - Make link text descriptive
- [2.4.5 Multiple Ways (Level AA)](./operable/navigable.mdx#245-multiple-ways-level-aa) - Provide multiple navigation methods
- [2.4.6 Headings and Labels (Level AA)](./operable/navigable.mdx#246-headings-and-labels-level-aa) - Use descriptive headings and labels
- [2.4.7 Focus Visible (Level AA)](./operable/navigable.mdx#247-focus-visible-level-aa) - Ensure focus indicators are visible

### 2.5 Input Modalities

Make it easier for users to operate functionality through various inputs beyond keyboard.

- [2.5.1 Pointer Gestures (Level A)](./operable/input-modalities.mdx) - Provide simple alternatives to complex gestures
- [2.5.2 Pointer Cancellation (Level A)](./operable/input-modalities.mdx#252-pointer-cancellation-level-a) - Allow users to cancel or undo actions
- [2.5.3 Label in Name (Level A)](./operable/input-modalities.mdx#253-label-in-name-level-a) - Ensure accessible names match visible labels
- [2.5.4 Motion Actuation (Level A)](./operable/input-modalities.mdx#254-motion-actuation-level-a) - Provide alternatives to motion-based controls
