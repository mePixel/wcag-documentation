# 4.1.2 Name, Role, Value (Level A)

## Requirement

For all user interface components (including but not limited to: form elements, links and components generated by scripts), the name and role can be programmatically determined; states, properties, and values that can be set by the user can be programmatically set; and notification of changes to these items is available to user agents, including assistive technologies.

## Understanding

Assistive technologies need to know the name, role, and value of all interactive elements to provide appropriate information and interaction methods to users.

- **ARIA4**: Using a WAI-ARIA role to expose the role of a user interface component
- **ARIA5**: Using WAI-ARIA state and property attributes to expose the state of a user interface component

## Examples

### Good: Native HTML Elements

Native HTML elements have built-in name, role, and value:

```html
<button type="button">Submit</button>
<a href="/about">About</a>
<input type="text" name="email" id="email" required>
<select name="country">
  <option value="us">United States</option>
</select>
```

### Good: Custom Components with ARIA

```html
<!-- Custom button -->
<div role="button" tabindex="0" aria-label="Close dialog" onclick="closeDialog()">
  ×
</div>

<!-- Tab interface -->
<div role="tablist" aria-label="Product tabs">
  <button role="tab" aria-selected="true" aria-controls="panel1" id="tab1">
    Description
  </button>
  <button role="tab" aria-selected="false" aria-controls="panel2" id="tab2">
    Reviews
  </button>
</div>

<div role="tabpanel" id="panel1" aria-labelledby="tab1">
  <p>Product description goes here.</p>
</div>

<div role="tabpanel" id="panel2" aria-labelledby="tab2" hidden>
  <p>Product reviews go here.</p>
</div>

<!-- Form with proper labels and ARIA -->
<form>
  <label for="email">Email Address</label>
  <input 
    type="email" 
    id="email" 
    name="email" 
    required
    aria-required="true"
    aria-invalid="false"
    aria-describedby="email-help"
  >
  <span id="email-help">We'll never share your email.</span>
</form>
```

### Bad: Custom Component Without Proper ARIA

```html
<!-- Custom button without role -->
<div onclick="submitForm()">Submit</div>

<!-- Form without labels -->
<input type="text" name="email" placeholder="Email">
```

## Common Failures

- **F59**: Failure of Success Criterion 4.1.2 due to using script to make div or span a user interface control in HTML without providing a role for the control
- **F68**: Failure of Success Criterion 4.1.2 due to not marking up a decorative image in HTML in a way that allows assistive technology to ignore it
- **F79**: Failure of Success Criterion 4.1.2 due to not identifying the purpose of a link in context in HTML
- **F80**: Failure of Success Criterion 4.1.2 due to not identifying the purpose of a link in a data table in HTML
- **F81**: Failure of Success Criterion 4.1.2 due to not identifying the purpose of a link in a nested list in HTML
- **F82**: Failure of Success Criterion 4.1.2 due to not identifying the purpose of a link in a collection of links in HTML
- **F89**: Failure of Success Criterion 4.1.2 due to not using an HTML label element to identify a form control in HTML
- **F90**: Failure of Success Criterion 4.1.2 due to not using an HTML label element to identify a form control in a data table in HTML
- **F91**: Failure of Success Criterion 4.1.2 due to not using an HTML label element to identify a form control in a nested list in HTML
- **F92**: Failure of Success Criterion 4.1.2 due to not using an HTML label element to identify a form control in a collection of links in HTML

## Best Practices

### 1. Use Native HTML Elements

Always prefer native HTML elements over custom implementations:

```html
<!-- Good: Native button -->
<button type="button">Submit</button>

<!-- Bad: Custom button -->
<div onclick="submitForm()">Submit</div>
```

### 2. Provide Accessible Names

Ensure all interactive elements have accessible names:

```html
<!-- Good: Button with text -->
<button type="button">Submit</button>

<!-- Good: Button with aria-label -->
<button type="button" aria-label="Close dialog">×</button>

<!-- Good: Button with aria-labelledby -->
<button type="button" aria-labelledby="close-btn-text">
  <span id="close-btn-text">Close</span>
  ×
</button>
```

### 3. Use Appropriate Roles

Use ARIA roles when HTML doesn't provide the needed semantics:

```html
<!-- Good: Custom tab interface -->
<div role="tablist" aria-label="Product tabs">
  <button role="tab" aria-selected="true" aria-controls="panel1" id="tab1">
    Description
  </button>
</div>
```

### 4. Manage States and Properties

Keep ARIA states and properties synchronized with the visual state:

```html
<!-- Good: Expandable section -->
<button 
  aria-expanded="false" 
  aria-controls="content"
  onclick="toggleContent()"
>
  Show more
</button>
<div id="content" hidden>
  Content goes here
</div>
```

### 5. Test with Assistive Technologies

Verify your components work with various assistive technologies:

- Screen readers (NVDA, JAWS, VoiceOver, TalkBack)
- Screen magnifiers
- Voice recognition software
- Alternative input devices

## Testing Checklist

- [ ] Verify all interactive elements have accessible names
- [ ] Check that roles are appropriate for each element
- [ ] Ensure states and properties are correctly set
- [ ] Test with screen readers to verify name, role, and value
- [ ] Verify keyboard navigation works correctly
- [ ] Test with multiple assistive technologies
- [ ] Check that dynamic updates are announced
